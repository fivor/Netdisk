# 隧道下载加速指南（CF Tunnel 链路优化）

## 背景：速度瓶颈在哪

`/dl` 下载链路：**用户浏览器 → CF 边缘 → cloudflared（家里） → 127.0.0.1:8100 → 磁盘**。

实测数据（2026-09-19，756MB 文件，直连绕过 Clash）：

| 环节 | 实测吞吐 |
|------|---------|
| 服务端磁盘 + FastAPI（127.0.0.1 回环） | **50.2 MB/s** —— 无瓶颈 |
| 经 CF 隧道（用户侧单连接） | **0.17 ~ 1.1 MB/s** ← 瓶颈全在这里 |
| 对照：家庭宽带上行（转存上传腿） | ~10 MB/s |

结论：瓶颈是 **CF 免费隧道链路**（国内用户访问 CF 边缘绕行海外 + cloudflared 回连边缘走默认 http2）。服务端代码已排除。

## 优化手段（按投入产出排序）

> 注：QUIC 已实测不可行（见下），当前最现实的组合是 **边缘缓存 + 用户侧多线程**。

### ① QUIC 实测记录：当前网络环境不可行 ❌

2026-09-19 深夜实测：`sc config Cloudflared binPath= "... --protocol quic ..."` + 重启后，隧道持续 530（cloudflared 无法连上 CF 边缘）——**出站 UDP 7844 被网络环境阻断**（家宽/路由器策略），已回滚 http2 并恢复（下线约 3 分钟）。

如果未来想再试：先在路由器放行出站 UDP 7844，或向 ISP 确认 UDP 国际链路可用；否则不要启用。默认 http2 虽慢但稳定。

### ② CF 边缘缓存（已在代码中实现，填三个环境变量即生效）

CF 默认按扩展名缓存 apk/exe/dmg/zip 等 —— 也就是说**边缘缓存今天就在半生效状态**（响应未显式控制）。本项目已实现确定性开关：

- `.env` 配置三项：`CF_PURGE_TOKEN`（CF API Token，权限 Zone.Cache Purge）、`CF_PURGE_ZONE`（Zone ID）、`CF_PUBLIC_ORIGIN=https://your-domain.example`
- 生效后：`/dl` 响应带 `Cache-Control: public, max-age=14400` → **同一链接的多用户重复下载直接吃 CF 边缘、完全绕过隧道**（≤512MB 文件，免费版单文件缓存上限）
- 任务删除时自动调用 CF Purge API 清缓存，兑现「任务删除即失效」承诺

适用场景：一个热门文件分享给多人下载——第一个（每个节点）慢，后面的都快。

### ③ 用户侧自助加速（无需改任何东西）

- **多线程下载器**：`aria2c -x16 -s16 "<链接>"` 或 IDM——/dl 支持 Range，高延迟链路上多连接成倍提速
- **浏览器插件/下载器走直连**：若 Clash 把 your-domain.example 代理出去了，给它配 DIRECT 规则
- **同一台电脑下载**：直接用 `http://127.0.0.1:8100/dl/<token>`，回环实测 50MB/s

### ④ 治本方案（大工程，按需）

| 方案 | 适用 | 代价 |
|------|------|------|
| 优选域名/自选 IP（DNS 层 CNAME 到优选 CF 节点） | 国内用户访问 CF 的路由优化 | 需 CF DNS 操作，优选 IP 会失效需维护 |
| frp + 国内/香港 VPS | 完全绕开 CF | 一台 VPS 的成本与运维 |
| Tailscale 组网 | 自己设备间下载（点对点直连） | 仅限加入组网的设备 |
| 家宽公网 IPv6 直连 + DDNS | 有公网 IPv6 且对方网络支持 v6 | 防火墙/前缀变化维护，安全面需评估 |

### 测速方法

```bash
python tools/measure_dl_speed.py "https://your-domain.example/dl/<token>" 8 3
```

直连（绕过 Clash）+ 浏览器 UA + Range 分片，每次只拉前 8MB，不耗完整流量。

## P1 —— 建议尽快修（6 条）

### 1. force 删除进行中的任务后，底层转存继续跑完（main.py + 前端）
- **位置**：`main.py api_task_delete`（622-646 行）＋ 前端删除流程（index.html 1717-1733 行，运行中任务自动带 `force=1`）。
- **问题**：删除路径**从不调用** `orch.cancel()` / `orch.cancel_group()`（全文件 grep 确认仅在 cancel 端点调用）。force 删除只删 DB 行，worker 继续执行：几十 GB 的上传照烧带宽、源盘配额与风控额度，结果写回被 `_safe_update` 静默吞掉。组合转存更糟：`_run_group_inner` 对已删除子任务 `store.get(tid) or {}` 得到空 dict → 状态判非终态 → **照常执行已删除目标的转存**。
- **修法**：删除 pending/running（或组内有此类）任务前先 `orch.cancel(task_id)` / `orch.cancel_group(gid)`，再删库。

### 2. OpenList 下载回退检测会误杀健康任务（openlist.py wait_copy）
- **位置**：`wait_copy` 331-337 行。
- **问题**：`dl_regress` 只增**永不清零**。两种良性场景都会让 `dl_bytes` 骤降到峰值 50% 以下：① 大文件「temp 落完 → temp 清空 → 目标盘索引尚未同步出 landed」的单轮交接窗口；② 并发中转开始/结束时 `temp_attributable()` 翻转（temp 归属从"可归"变"不可归"，dl 直接从 landed+temp 掉到 ~0）。累计 3 次（约 15-20 秒）即抛"反复从头重试"中止**完全健康**的传输——20GB 级任务在第二个任务恰好并行启动时极易命中。
- **修法**：`st.dl_bytes >= max_dl_seen * 0.5` 时把 `dl_regress` 归零；归属模式翻转的那一轮跳过回退检测并重置 `max_dl_seen` 基线。

### 3. 夸克「自己的分享」主路径丢失 self_share 标记（quark.py:241-243）
- **问题**：`_self_share_ref` 两条路径返回的 SavedRef 不一致——兜底 BFS 路径（288-290 行）带 `self_share=True`，**主路径（自底向上，3~5 次请求即可成功，实际几乎总是走这条）漏了该标记**。后果：组合转存「本人链接 + 同源目标应判失败并给人话原因」的语义失效——用户确认过的产品行为悄悄失效，还会白白消耗一次分享配额。
- **修法**：主路径 return 补上 `self_share=True`。

### 4. 夸克分享列表与定位均单页截断（quark.py）
- **save**（126-132 行）：分享详情写死 `_size: 50` 不翻页 → **>50 个文件的分享静默只转前 50 个**，无任何提示。
- **locate**（375-378 行）：单页 `_size: 100` 不翻页 → 转存目录（所有任务共用一个「转存」目录，只增不减）超过 100 条后，跨平台转存到夸克开始随机报「未找到转存后的文件」——**这正是百度侧 `_list_all` 当年修过的同款问题**，夸克漏修。
- **附带**：`_dir_fid` / `_ensure_work_dir` 也是单页 100（子代理同报）。
- **修法**：三处补翻页循环（对齐 baidu `_list_all` 写法）；save 超过一页时提示总数。

### 5. 阿里 token 并发刷新竞态，可导致凭据永久失效（ali.py:118-137）
- **问题**：`_token` 注释声称"刷新为幂等操作，极端并发至多多刷一次"——**前提错误**：阿里 refresh_token 是轮换型（刷新即作废旧值）。两个 worker 同时缓存未命中 → 都拿同一个 current_rt 去刷 → 后写盘者可能把 `ali_token_state.json` 回退成已作废的旧 token；`_api` 的 401 强刷兜底用的也是这份坏状态 → 死循环失败，只能人工重新获取 refresh_token。
- **修法**：刷新区加互斥（threading.Lock，抢到锁后先复查缓存再刷；刷新本身在锁外 await，持久化前二次确认 current_rt 未被他人推进）。

### 6. 前端登出竞态：在飞响应把 ADMIN 置回 true（index.html loadStatus）
- **问题**：`loadStatus` 入口判了 `AUTHED`，但 `await api(...)` 之后**不再复查**。退出登录后返回的在飞响应会执行 `ADMIN = !!s.admin` → 访客态残留管理员身份：阿里胶囊解锁渲染、触发 `loadLocalFiles()` 用空 token 打接口（若 APP_PASSWORD 未设则直通后端）→ 再次 401 → 弹「登录已失效」误导 toast。`tryRestoreSession`/`loadTasks` 同型。
- **修法**：所有 async 响应处理入口加 `if (!AUTHED) return;`（或引入会话序号，过期响应直接丢弃）。

## P2 —— 应修（18 条）

**后端**

7. **confirm_continue 解析失败返回 500**：orchestrator.confirm_continue 重抛 ParseError，main.py 只捕 KeyError（688-691 行）→ 应捕 ParseError 回 422。
8. **百度 async 转存后立即定位，无重试**：save 用 `async=1` 提交（215 行）却同步调 `_locate_saved_files`，服务端转存未落稳时间歇报「转存完成但未找到」→ locate 加 2~3 次退避重试。
9. **取消信号/进度峰值泄漏**：`_cancelled`、`_peak_progress` 只在 `_exec_one` finally 清理；取消时从未执行的 pending 子任务（`_cancel_rest` 路径）永远不清理，长运行慢性泄漏。
10. **恢复后进度峰值不复位**：confirm_continue 重置 DB progress=1，但 `_peak_progress` 还压着 30 → 前端进度从 30 起跳（外观问题）。
11. **token 比较非常数时间 + 登录无速率限制**：`x_auth_token == pwd`、`== _admin_token(pwd)` 均为普通比较（`secrets.compare_digest`）；/api/auth/login 可无限暴力尝试。
12. **只设 ADMIN_PASSWORD 不设 APP_PASSWORD 时共享接口全裸**：`require_token` 只检查 `app_password` 非空 → 此组合下 /api/transfer 对所有人开放，且启动告警只覆盖"两个都未设"。至少补告警，最好改为"任一口令存在即启用鉴权"。
13. **布尔环境变量大小写陷阱**：`RELAY_REAP_FORCE=FALSE` 会被解析为**开启**（`not in ("", "0", "false")` 未含 "FALSE"/"False"）——这是个"明知会毁数据"的危险开关。统一 `.lower()` 解析。
14. **提取码正则误报**：parser `_PASSWORD` 的 `code` 备择可被 URL 查询串 `source=abcd`/`encode=xxxx` 误命中 → 提取码张冠李戴且难以察觉；`validate_password` 对纯空白输入返回 `""` 而非回退到解析值。
15. **损坏 JSON 打挂列表接口**：`db._row_to_task` 对 result_files/progress_detail 等直接 `json.loads`，一条损坏记录让 /api/tasks 整体 500 → try 包裹降级为空值。
16. **async 路由里的同步 SQLite**：`async def` 端点直接调 `store.*`，`_write` 全局锁被 worker 持有时事件循环被卡（量大后响应抖动）→ 端点改 `def`（FastAPI 自动扔线程池）或 `run_in_executor`。
17. **copy_tasks done 表全量轮询**：wait_copy 每 5 秒全量拉 undone+done 两张表，done 随时间无限积累 → 长任务后期每轮传输量线性膨胀（OpenList 侧是否支持分页/裁剪值得查）。

**前端**

18. **轮询竞态**：loadTasks 2s 一发且无 in-flight 守卫/序号，慢响应会覆盖较新状态（UI 回退、重复触发 setMsg/maybeNotify）→ 加"请求序号，过期丢弃"。
19. **401 错误提示误导**：api() 抛 `Error("unauthorized")`，submitTask 的 catch 显示"网络错误：Error: unauthorized"→ 对 401 给"登录已失效"文案。
20. **needs_confirm 容量靠正则从 message 抽取**：`/约\s*([\d.]+)GB/` 匹配后端文案 → 后端改一个字前端就静默丢提示 → 容量应落结构化字段（over_files 里带上或独立字段）。
21. **showConfirm 全局单例**：连续两次弹窗（如快速点两行删除）第一个 Promise 永久悬挂 → 简单加队列或直接禁用第二次调用。
22. **Dedup 跨 owner 复用**：600s 窗口内他人提交同链接会拿到你的 task_id（内容不可见但存在探测面）；记录列表 limit=100 封顶，更老记录任何翻页都看不到。两条均为已知设计边界，建议：dedup 命中校验 owner 一致才复用；文档写明 100 条上限。

# 大文件跨平台转存 · 事故复盘与解决方案

> 环境：OpenList v4.2.6 / pan-transfer（FastAPI）/ 家宽 ~146Mbps 下行 · ~80Mbps 上行
> 事故对象：quark → 百度，源目录「使命召唤 cod 全系列：1-21 中文版」**实测 1.30 TB**（19 个游戏 / 215 个文件，最大单文件 **79 GB**）

---

## 0. 事故时间线（实测数据）

| 时刻 | 事件 |
|---|---|
| 20:01 | 提交 quark→百度（三连：幻兽帕鲁 / 极限竞速 FH6 / 使命召唤合集） |
| 20:07 | 诊断：进度卡 56%、openlist `eth0` rx **25 MB/s** / tx **1 MB/s**、`data/openlist/temp` 5 个临时文件持续增长 |
| 20:12 | 我们侧任务因 **`wait_copy` 10 分钟硬超时** → 标记 failed；**OpenList 后台仍在继续复制** |
| 20:16~20:20 | 主动取消全部复制任务（186 个）；temp 自动清空（19.7 GB → 0）；G 盘 384.6 → **404.3 GB** |

**根因链一句话**：完成判定看错了对象 → 假成功 → 链接不全；超时太短且超时不同步停后台 → 记录失败但硬盘继续被吃。

## 1️⃣ 「显示成功但文件不全，后台还在跑」

### 根因（已取证）
`/api/task/copy/done` 实测显示，OpenList 对**目录**的 `fs/copy` 会拆成**每个节点一个任务**：

```
state=2 (成功)  copy [/quark](/微信分享/游戏/极限竞速：地平线6)          → [/baidu](/转存)        ← 目录级
state=2 (成功)  copy [.../极限竞速：地平线6/v440.853)                 → [.../极限竞速：地平线6] ← 子目录级
state=4 (取消)  copy [.../v440.853/FH6.zip)                          → [...]                  ← 真正的大文件
state=4 (取消)  copy [.../v440.853/FH6.z01)                          → [...]
```

**目录级任务在「子任务入队完毕」时就置为 done**，而真正搬运数据的文件级任务还挂在 undone。
`wait_copy()` 只盯 `fs/copy` 返回的 task id（或按名字模糊匹配目录名）——看到那个"目录任务"done 就 `return` 成功。

**后果**：`_relay` 立刻调用目标盘 `share()` 生成分享链接 → **链接里的文件必然不完整**（且不会自愈）。

### 解决方案
**完成判定必须改为「目的地校验 + 队列归零」双重条件**：

```python
def _relay(...):
    ...
    _submit_copy(...)                       # 提交
    _wait_and_verify(...)                   # 新逻辑（替换 wait_copy）
    # 只有校验通过才继续 share() 生成链接

def _wait_and_verify(src_ref, dst_dir, task_ids, progress):
    src_total, src_map = enumerate_tree(src_dir)      # 源：名字 → 大小（任务开始时算一次）
    while True:
        if cancelled: raise TaskCancelled
        # ① 队列归零：undone 中不存在 dst 属于本任务目标目录的任务
        pending = openlist.pending_tasks_under(dst_dir)     # 过滤 name 含 "to [<mount>](<dst_dir>...)"
        # ② 目的地校验：递归枚举 dst，核对名字+大小
        dst_map = enumerate_tree(dst_dir)
        done_bytes = sum(dst_map.values())
        inflight = sum(temp_file_sizes())                   # 在途（下载中）
        # ③ 进度/速度/ETA
        progress(pct=(done_bytes+inflight)*100//src_total,
                 msg=f"已传 {gb(done_bytes)}/{gb(src_total)} GB",
                 speed=..., eta=...)
        if not pending and _match(src_map, dst_map):        # 齐全且大小一致
            return
        sleep(10)
```

- `_match`：源里每个文件都能在目标找到同名且 **大小一致** 的项（大小不符 = 传坏/半截）。
- 校验不过就**继续等**，绝不放行 `share()`。
- 兜底：若源里有"目录"节点，递归展开比对（不要只比顶层）。

**收益**：杜绝假成功；分享链接永远对应完整内容。

## 2️⃣ 「是否先下载到本地？会删吗？本机文件为什么是空的？」

| 问题 | 答案 | 证据 |
|---|---|---|
| 先下载到本地吗？ | **是**。跨驱动 copy 走「下载到本地临时文件 → 上传目标」，**不是流式** | `data/openlist/temp/file-*` 生成并持续增长 |
| 上传后删除吗？ | **会删**。取消后 temp 立即清空（5 个 → 0）；正常结束同样会清 | 实测取消后 temp=0 个 / 0 GB |
| 本机文件页为什么空？ | **正常，不是 bug** | 该页只列 `LOCAL_DIR/转存`（`/data/downloads/转存`），是**本机高速（local 目标）**的落盘目录；而 quark→百度 的临时文件在 **OpenList 自己的 `data/openlist/temp`**，两者完全无关 |

> ⚠️ 顺带纠正一个历史错误：方案文档里写的「数据边下边传、**不落盘**」**不成立**。跨驱 copy 会落盘到 OpenList temp。

**改进建议**
- 页面文案改为 **「本机高速下载（本机落盘）」**，避免误解。
- 可增加一个**「OpenList 中转缓存」**信息块（显示 temp 占用/在途文件），让"看不见的落盘"可见。

## 3️⃣ 「上传真的只有 1MB/s 吗？」

**我测到的是 openlist 容器 `eth0` 的 tx ≈ 1 MB/s（6~8 秒采样窗口）。这是真实观测，但只代表采样时段。**

客户端快的原因（推断 + 机理）：
1. 官方客户端走**百度自家上传协议**（可能多线程切片 + 加速通道）；
2. OpenList 走的是**模拟网页 / 开放接口**，百度对第三方上传普遍限速，非会员尤甚；
3. OpenList 跨盘 copy 若**单线程串行上传**，聚合吞吐也上不去。

**建议做一次受控测速**（结论要数据说话）：

```
选一个已知大小的文件 → quark→百度 单文件转存
记录：耗时 / tx 均值 / 文件大小 → 得到「第三方上传真实速率 R」
```
这个 R 是后面所有参数（超时、ETA、并发）的地基。

同时查 OpenList 百度驱动的上传相关配置（分片/并发）是否能调。

## 4️⃣ 「实时显示完整下载/上传进度 + 预计剩余时间」

**现状**：`wait_copy` 里 `progress(55, "复制中")` 是**常量** → 整个复制期进度条不动（你看到的"卡 56%"）。

**方案：三段式计量（全部可实测，无需 OpenList 支持字节进度）**

| 指标 | 取法 |
|---|---|
| `total_bytes` | 任务开始时**递归枚举源目录**累加（缓存） |
| `done_bytes` | 每 15s **递归枚举目标目录**累加 |
| `inflight_bytes` | `data/openlist/temp` 各文件大小之和（把该目录**只读挂**进 pan-transfer） |
| 进度 | `(done + inflight) / total` |
| 下载速率 | `Δ(inflight + done)/Δt` 或容器 rx |
| 上传速率 | `Δdone/Δt` 或容器 tx |
| ETA | `(total - done - inflight) / rate` |

**页面展示建议**：
```
已传 123.4 / 1330.0 GB（9%）
下载 25.1 MB/s · 上传 1.0 MB/s · 预计剩余 3 天 4 小时
下载中（在途 18.5 GB）
```

要把 openlist 容器网络计数暴露给页面，最干净的做法：**给 pan-transfer 挂载 `data/openlist/temp:ro`**（读在途），速率用差分算，避免依赖 docker API。

## 5️⃣ 「能不能下一点传一点，分批搞完 1.3TB？」

**好消息：OpenList 已经在按「文件」分批**——逐文件 `下载 → 上传 → 删临时`，并发约 5。
**坏消息：单个文件不可拆**（必须完整下载才能上传），所以：

- ✅ 能跑的前提：**最大单文件 ≤ 可用空间**
- ❌ 本例：最大单文件 **79 GB**，峰值占用 ≈ 并发 × 平均文件大小，1.3TB 总量对 385GB 余量——**总量不是问题（临时文件会释放），单文件才可能爆**

**改进方案**
1. **并发降到 1**：峰值占用 ≈ 单个文件大小，把"分批"做到最安全（代价：慢）。
2. **前置空间校验（必做）**：任务开始前算
   - `源总大小` 和 `最大单文件大小`
   - 与 `剩余空间` 比较，不满足 → **直接拒绝**并给中文提示：
     > 「最大单文件 79 GB，当前剩余 385 GB，可继续；若单文件超过剩余空间将无法中转」
3. **超限时给出替代路径**：换「本机高速」目标（仍是落盘，同样受空间限制）、或分段分享、或手动。

> 结论：**1.3TB 可以分批过**（只要没有单文件超过剩余空间），但**耗时以天计**，且必须先把第 1、6 条修好，否则"分批"过程中随时假成功/假失败。

## 6️⃣ 「10 分钟超时太短；超时后把后台任务也停掉」

**两个独立缺陷**：
- `wait_copy(timeout=600)` 对 1.3TB 是荒谬的（连一个 79GB 文件都传不完）；
- 超时**只失败我方记录**，OpenList 任务毫发无伤继续跑。

**方案**

**(a) 用「停滞检测」替代固定超时**
```
只要 done_bytes + inflight_bytes 还在增长 → 不判超时
仅当连续 STALL_MIN 分钟（默认 15 分钟）零增长 → 判「卡死」并收尾
上限：RELAY_MAX_HOURS（默认 24h）兜底
```

**(b) 超时/失败/取消 → 同步收尾 OpenList**
```python
def _abort_openlist(dst_dir, task_ids):
    for tid in task_ids: openlist.cancel(tid)                 # 精确：提交时保存的 id
    for t in openlist.undone():                              # 兜底：目标目录前缀匹配
        if t["name"].endswith(f"to [/baidu]({dst_dir}...)") or dst_dir in t["name"]:
            openlist.cancel(t["id"])
```
触发点：`wait_and_verify` 判卡死、`TaskCancelled`、任何异常兜底、**服务启动时的孤儿回收**。

**(c) 分享链接生成时机**
只有在「目的地校验通过」后才 `share()`；中途取消/卡死 → 任务标记失败/取消，**不产出链接**。

## 8. 需要你拍板的参数

| 参数 | 建议默认 | 说明 |
|---|---|---|
| 停滞判定窗口 `STALL_MIN` | 15 分钟 | 连续无增长才判卡死 |
| 硬上限 `RELAY_MAX_HOURS` | 24 小时 | 兜底 |
| OpenList 复制并发 | **1**（最稳）/ 2~3（折中） | 决定临时文件峰值占用 |
| 单文件/剩余空间安全系数 | 需要 1.2× 余量 | 前置校验阈值 |
| 上传速率占位值 R | 待受控测速 | 用于 ETA |
